# Сквозная проверка: настоящий клиент против настоящего сервера

Все ошибки, из-за которых игроки не могли зайти на сервер, жили в одном месте — на пути
игрока: загрузка конфига, знакомство клиента с сервером, проверка при входе. Ни один
существующий тест этот путь не проходит целиком: Java-тесты работают с API без игры, а
`runtime-agent-check.js` подключается библиотекой, а не настоящим модом.

Стенд ниже поднимает **настоящий сервер Minecraft** и **настоящий клиент**, оба с тем самым
файлом, который ставят себе люди. Готового не подкладывается ничего: у сервера нет проекта,
пока он не запустится и не создаст его сам; у клиента нет проекта, пока он не зайдёт и игрок
не согласится. Это и есть последовательность, которую надо проходить на настоящей программе.

## Как поднять

```bash
npm run minecraft:build
```

```bash
npm run e2e:stand -- 26.2
```

Создаётся `.qa/fabric-26.2-e2e/` с миром, `fixture.json` и одним и тем же модом в
`server/mods` и `client/mods`. Каталог одноразовый: повторный запуск стирает прежний.

Сервер (API на 43077, игра на 43565, RCON на 43575):

```bash
cd minecraft/udmc-sync-fabric && ./gradlew runServer -Pminecraft_version=26.2 -Pudmc_packaged_test -Pudmc_run_dir=<путь>/.qa/fabric-26.2-e2e/server
```

При первом запуске сервер заводит проект и пишет код привязки — в консоль и в
`server/config/udmc-pairing.txt`. Забрать проект и сообщить серверу его адрес:

```bash
npm run e2e:admin -- pair
```

Это ровно те три действия, которые делает панель: читает код, обменивает его на доступ,
отправляет серверу адрес, по которому до него только что дозвонилась. Дальше — правило входа:

```bash
npm run e2e:admin -- require-on
```

Клиент, который сам подключается к стенду:

```bash
cd minecraft/udmc-sync-fabric && ./gradlew runClient -Pminecraft_version=26.2 -Pudmc_packaged_test -Pudmc_run_dir=<путь>/.qa/fabric-26.2-e2e/client -Pudmc_quick_join=127.0.0.1:43565
```

Порт агента стенд пишет в `server/config/udmc-sync.json` до первого запуска: он больше не
запекается в файл, и так его задаёт владелец на настоящем хостинге.

## Что проходить

| Сценарий | Что сделать | Что должно быть |
| --- | --- | --- |
| Проект рождается | запустить сервер начисто | код в консоли и в `config/udmc-pairing.txt`, одинаковый |
| Код переживает перезапуск | перезапустить сервер | тот же код, файл на месте |
| Привязка | `e2e:admin -- pair` | доступ получен, `адресДляИгроков` заполнен, файл кода исчез |
| Код одноразовый | повторить `pair` | отказ `PAIRING_ALREADY_DONE` |
| Привязка по RCON | взять код командой `udmc pair` через RCON | код и порт API в одной строке ответа |
| Раздача клиента | посмотреть `раздаётсяКлиент` | версия агента, ничего загружать не надо |
| Знакомство | зайти клиентом | в логе клиента `UDMC was offered project` |
| Незанятый клиент | `require-on`, зайти | отказ: «установлен, но ещё не настроен ни на какую сборку» |
| Согласие | вернуться на главный экран, принять | конфиг клиента заполнен, синхронизация пошла |
| Обычный вход | после согласия зайти снова | игрок в мире |
| Мода нет | пустой `mods`, флаг `-Pudmc_test_without_agent` | отказ с двуязычной инструкцией и версиями сервера |
| Чужой проект | подставить клиенту конфиг другого проекта | «две сборки не живут в одной папке mods» |
| Смена ключа | подменить `manifestPublicKey` в конфиге клиента | «ключ сервера изменился», ничего не применено |
| Восстановление | сохранить копию, поднять сервер начисто, привязать с копией | новый сервер подписывается прежним ключом |
| Самообновление | опубликовать пересобранный JAR, запустить клиент **без** `-Pudmc_quick_join` | «Обновление UDMC готово», после выхода файл в `mods` заменён |

Последняя строка — про гонку, а не про обычный путь. Клиент чинит себя сам при каждом
запуске, поэтому автовход (`-Pudmc_quick_join`) обгоняет фоновую синхронизацию и показывает
отказ, которого игрок в жизни не увидит. Совет на экране должен быть «перезапустите игру», а
не «скачайте файл».

**Fabric API обязателен в стенде.** Положите его и в `client/mods`, и в `server/mods`: без него
проверка проходит там, где в жизни ломается. Fabric API сам обрабатывает каналы входа и
отменяет ванильный вызов — именно на этом UDMC однажды перестал отвечать серверу, и без него
в стенде это не воспроизводится. То же касается любого мода, который трогает сеть.

Скриншот обязателен: две ошибки этого набора — невидимая строка и кнопка не в том блоке —
программные проверки не видели вовсе.

## Пройдено на текущем коде

Проверка клиента живёт в фазе configuration (`docs/client-verification.md`). Прогон на
Minecraft 26.2, Fabric API с обеих сторон:

| Что | Итог |
| --- | --- |
| сервер создал проект и код | код в консоли и в файле, совпадают |
| привязка кодом | доступ получен, адрес записан, код потрачен |
| сервер раздаёт свой файл | `раздаётсяКлиент: 0.19.0`, ничего не загружалось |
| клиент получил предложение проекта | `UDMC was offered project udmc-main at http://127.0.0.1:43077` |
| незанятый клиент при `require-on` | отклонён, причина читается и объясняет, что делать |
| без требования | игрок вошёл в мир |

Строка про предложение — главная: она доказывает, что новый канал уживается с Fabric API, а
не отбирается им. Экран согласия в игре на этом прогоне не проверялся глазами.

## Матрица конфигураций

Полная матрица, по которой проверяется проверка клиента, — в `docs/client-verification.md`,
раздел «TEST PLAN». Коротко: с полным Fabric API и без него, на клиенте и на сервере по
отдельности, все три версии Fabric и NeoForge, ванильный клиент без загрузчика, за прокси.
Каждая из четырёх прежних попыток чинить проверку работала ровно в одной конфигурации и
ломалась в другой — поэтому проходить надо всю матрицу, а не ту строку, где болит.

## Почему не в CI

Прогон требует настоящих клиента и сервера Minecraft с окном и загрузкой ассетов: это
минуты и графическая среда. Проверка делается руками перед выпуском, который меняет агентов.
