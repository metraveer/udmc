# Рабочее соглашение

## Кто выпускает релизы

**Тег версии ставит только владелец проекта.** Ассистент не выпускает релиз по своей
инициативе — даже когда изменения готовы, протестированы и просятся наружу.

Как это работает на практике:

1. Изменения накапливаются в `main`. После каждой задачи — тесты, сборка, проверка глазами,
   коммит и `git push`. Ничего больше.
2. Когда владелец пишет «выпускай» (или называет версию), ассистент проводит выпуск целиком:
   поднимает номер, пишет раздел в `CHANGELOG.md`, коммитит, ставит тег, дожидается сборки
   на GitHub и публикует черновик релиза.
3. Если ассистент считает, что пора выпускать, он это предлагает одной строкой и ждёт ответа.

Смысл правила: выпуск виден всем, кто уже установил приложение — оно само предложит
обновиться. Решение о том, что показывать людям и когда, остаётся за владельцем.

## Сколько это стоит

Репозиторий `metraveer/udmc` **публичный**, а для публичных репозиториев GitHub Actions на
стандартных раннерах бесплатны и без лимита минут. Один прогон CI или Release занимает
12–16 минут, и эти минуты не расходуют никакой квоты.

Квота в 2000 минут в месяц действует только для приватных репозиториев. Если репозиторий
когда-нибудь станет приватным, это правило нужно пересмотреть: тогда имеет смысл собирать
установщик на компьютере (ключ подписи лежит в `~/.udmc/updater.key`) и загружать готовые
файлы в релиз вручную.

Что действительно стоит беречь — внимание владельца. Поэтому:

- Связанные правки уходят одним пушем, а не пятью подряд: пять пушей — это пять прогонов CI
  и пять писем о результате.
- CI не запускается на тегах (`ci.yml` слушает только ветки), поэтому выпуск даёт один
  прогон Release, а не два параллельных.
- Новый пуш отменяет предыдущий незавершённый прогон CI (`cancel-in-progress`).

## Проверка перед пушем

Порядок, который ловит то, что не ловит следующий шаг:

```bash
npm test
```

```bash
cd apps/admin-desktop/src-tauri && cargo build
```

Затем — нативная проверка глазами: мок-агент `node scripts/dev/mock-agent.mjs 46000 3`
(печатает код привязки), запуск отладочной сборки с `UDMC_TEST_PROFILE=<имя>` и
`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=<порт>`, скриншоты через CDP; снимки для README и документации — `node scripts/dev/docs-screenshots.mjs docs/images`.
Программные проверки регулярно пропускают то, что сразу видно на снимке:
наложения, лишние линии, кнопки не в том блоке. Скриншот обязателен для любой правки вёрстки.

Тестовый профиль есть только в отладочной сборке и держит свои данные в `%TEMP%`, отдельно от
настоящего хранилища и настоящего сервера владельца.

Если правка задевает агентов — конфиг, вход игрока, синхронизацию, — этого мало:

```bash
npm run e2e:login -- 1.21.1
```

```bash
npm run e2e:login -- 1.21.1 fabric-api
```

Каждая команда поднимает настоящий сервер Minecraft с тем самым файлом, который ставят игроки,
привязывает его как панель и заходит десятью разными клиентами: пять неверных должны быть
развёрнуты с правильной причиной **до того, как игра отправила хоть что-то из реестров**,
верные — войти, а с выключенным правилом неверные должны войти и получить объяснение. Вторая
команда ставит на сервер весь Fabric API — конфигурацию настоящего сервера, в которой каждая
прежняя проверка входа ломалась по-своему. Обе гоняются в CI. Экраны клиента и версии 26.x они
не покрывают — для них остаётся ручной стенд `docs/end-to-end-stand.md`.

Что чем проверяется и чего автоматика не ловит: `docs/testing.md`. Оттуда же два правила,
которые стоили двух выпусков: **проверка, которая может молча перестать проверять, хуже, чем
её отсутствие**, и **факт, записанный дважды, идёт в `scripts/consistency.test.js`**.

Все ошибки, из-за которых игроки не могли зайти, жили именно там, куда не доставал ни один
прежний тест.

## Чего нельзя менять

**Мод один и тот же для сервера и для игроков, и внутри него нет ничего.** Ни ключей, ни
адреса, ни названия проекта. Проект создаётся на самом сервере при первом запуске, панель
забирает его по коду привязки, клиент узнаёт всё от сервера при входе. Это снимает целый класс
поломок — «поставил файл от другого проекта», «остался конфиг от старого сервера», «сервер
раздаёт версию, которой ни у кого нет», — и делает невозможной самую дорогую ошибку: отдать
игрокам файл с закрытым ключом проекта. Возвращать персонализацию нельзя.

Из этого следуют правила, которые легко нарушить по невнимательности:

- в файл мода ничего не дописывается; панель отдаёт ровно те байты, с которыми собрана;
- файл со встроенными настройками отвергается: это может быть только старый персональный;
- закрытый ключ подписи не ходит по сети при привязке. Он покидает сервер только по явному
  запросу владельца за резервной копией;
- номер в вопросе входа (`QUERY_PROTOCOL`) заморожен на 2. Клиенты 0.19.0 читают вопрос по
  позициям, и удлинённый вопрос отнимет у них экран, который объясняет, что установить. Всё
  новое едет отдельным каналом.

**Minecraft ниже 1.20.2 не поддерживается и поддержан быть не может.** Проверка клиента при
входе живёт в фазе configuration, а она появилась в 1.20.2; в версиях ниже её нет вовсе, и
единственная альтернатива там — канал фазы входа, который на реальных сборках отбирает себе
Fabric API. Это измерено, а не предположено. Прежде чем добавлять версию в
`minecraft/agent-catalog.json`, прочитайте `docs/supported-minecraft-versions.md`.

Решение о том, как устроена проверка, и разбор отвергнутых вариантов: `docs/client-verification.md`.
Менять транспорт проверки без прогона по матрице конфигураций из этого документа нельзя:
каждая из четырёх прежних попыток работала ровно в одной конфигурации и ломалась в другой.

## Выпуск, когда он разрешён

```bash
npm run release:build -- patch
```

Дальше: раздел в `CHANGELOG.md`, коммит, `git push`, `git tag vX.Y.Z && git push origin vX.Y.Z`.
Сборка на GitHub делает подписанный установщик и `latest.json`, кладёт их в черновик релиза.
Черновик нужно опубликовать — только после этого приложения у людей увидят обновление.
Подробности: `docs/release-checklist.md`.
